---
title: ACE Inventory
---

Experimental PC-only MVP candidate for **modifier + Move batch transfers**,
with configurable small and large batches (default **5 and 10**) and **All that fit**.
Includes compact item and container metrics with per-player display preferences.
It is not included in ACE All in One and is not production-ready.

## Loading

1. In Arma Reforger Tools, scan the repository's `addons` directory for projects.
2. Open `ACE Inventory` (`addons/inventory/addon.gproj`).
3. ACE Magazine Repack is optional. Load it separately if magazine repacking is
   desired; ACE Inventory does not require it.
4. Compile Game scripts in Script Editor. Resolve compilation errors before testing.
5. Open a test world with inventory containers and an enabled arsenal.
   The development guide recommends the vanilla `MpTest` world.

The project intentionally has no resource database checked in. Allow Workbench
to generate its resource database when registering/opening the project.

## Inventory metrics

- Item tooltips show total compartment count, total storage capacity, largest available pocket dimensions, item volume, item dimensions and the original weight display on one line.
- Container headers show total free volume and the largest single pocket's free volume, for example `2.4(0.9) L`.
- Header dimensions show the largest available pocket dimensions, followed by the dimensions of the pocket with the most free volume, for example `15³(5³) cm`. Ties for most free volume use the longest-axis dimension ranking.
- Matching formatted values omit the parentheses. Cubes use `15³ cm`; other shapes use `15x10x5 cm`.
- Header counts include only pockets with positive remaining volume. Multi-compartment items retain the count at `1` and `0`; single-compartment items hide it. Tooltips retain the total count.
- Full and overfilled pockets are excluded from available dimensions. Missing or invalid measurements hide the affected readout.

Under **Settings → ACE Inventory**, independently toggle **Show dimensions**, **Show compartment count** and **Show single-pocket max values ()**. All three default to enabled and are saved locally per player. Changes refresh existing readouts without reopening inventory. Turning off single-pocket max values hides both parenthesized values, leaving main values unchanged.

Volume and dimensions are separate native inventory properties. Free space cannot be combined across pockets, and the largest available dimensions may belong to a different pocket than the one with the most free volume. These readouts are storage information, not a fit guarantee; other native restrictions can prevent a transfer. Metrics do not change item sizes, capacities or transfer rules.

Metrics are provided by ACE Inventory, not ACE Core. ACE Core is not required.
Settings labels currently have English translations; additional translations can be added through the addon's string table.

## Controls and scope

**Default quick transfer:** use the vanilla **Move** action on the source stack or arsenal
catalog item while holding **left Ctrl** for the small batch (default five).
Hold **left Ctrl + left Shift** for the large batch (default ten).
Hold **left Shift without left Ctrl** for **All**. Left Ctrl + left Shift takes
precedence and selects the large batch, not All.
Move uses the player's existing bindings (normally **X or right-click**), including
custom rebindings; ACE Inventory does not add fixed mouse/X shortcuts.
The lower-left navigation bar shows **Ctrl / Move 5**, **Ctrl + Shift / Move 10**
and **Shift / Move All**, alongside the vanilla Move hint showing its current
bindings. Numeric labels use the configured batch sizes. These are informational
modifier hints: pressing a modifier alone does not move anything. They remain
visible when vanilla shows its Requisition, Return, Pickup, Drop or Move hint.
They inherit vanilla's availability rules rather than adding separate checks.
The hint keys have vanilla hold indicators: keep the quantity key(s) held while
using Move. There is no minimum hold delay.
Right-side modifier keys do not select a batch with the default bindings.
The quantity is captured when Move fires, so releasing modifiers does
not change a pending batch. Incoming small/large quick transfers use compatible player deposit storages,
regardless of which player container is displayed. Incoming **All** transfers
instead target only the currently displayed player container, including ground
pickup, external-container pickup and arsenal acquisition. Open the desired
player container before clicking. The target is the selected clothing item or
bag, including all compatible pockets inside it, not just one internal storage.
All stops when that item is full rather than spilling into a different clothing
item or bag. For arsenal acquisition, native resource-storage selection is
repeated inside the captured target root for each item; physical transfers use
the equivalent scoped item-storage selector for their captured target roots. Automatic
destination selection is repeated per item, so filling one pocket does not stop
a batch when another player storage can accept the remainder. Player items go
to the currently open external container. If the opposite panel is showing the
ground rather than a container, modified Move on a player stack drops up
to the selected quantity. Modified Move on a loose ground stack picks up
to that quantity. With an arsenal
open, modified Move on a player stack returns/refunds up to that many eligible
items rather than dropping them on the ground.

Three modifier-state actions are attached to vanilla's active `InventoryMenuContext`.
When native `Inventory_Drop` (PC quick transfer) or `Inventory_Move` fires,
the current modifier values are captured:
Ctrl + Shift takes precedence over Shift, then Ctrl. There are no latched
modifier listeners or separate custom transfer listeners. Deferred resolution
executes the captured batch once, or the vanilla single-item move once if no
modifier was held. This input-dispatch step needs regression testing, particularly
with rebound Move inputs.
There are no batch-drag overrides.

**Dragging:** always uses vanilla behavior, including Magazine Repack behavior
when that addon is loaded, regardless of modifiers or a pending batch. Dragging does not select a
batch quantity. If an ordinary operation changes a snapshotted source, the batch
stops when it detects that change; it does not undo the ordinary operation.
If modifier bindings are unavailable, ordinary native inventory actions remain available.

After updating the addon, stop Play mode and reload the Workbench project
(or restart Workbench), then re-enter Play mode. Recompiling Game scripts alone
does not reload changed input bindings.

- Normal inventory: move up to the selected quantity from the selected visible stack.
- Arsenal: request up to the selected quantity of the catalog item through the
  native arsenal acquisition path, or return up to that many physical items through
  the native refund path. Items containing non-refundable contents are rejected.
- Ground: insert existing loose entities into inventory, or remove stored
  entities to the ground, through the normal native pickup/drop APIs.
- Capacity, compatibility and native arsenal rules may reduce the result.
- Releasing modifiers after Move fires does not change the captured quantity.
- All dragging keeps the existing inventory/magazine-repack behavior.

For All, physical transfers and arsenal returns snapshot the entire selected
visible stack, not every matching item across inventory. They stop at source
exhaustion, changed membership, cancellation or native rejection. Items added
to the stack after the snapshot are not included. Arsenal acquisition has no
finite source stack: it requests until native rules reject the next item or the
configured All ceiling is reached (default **100 confirmed acquisitions**).
The ceiling does not truncate physical stacks or arsenal returns.

Stored-stack snapshots enumerate the current navigation storage's physical
contents, including clothing pockets, rather than the UI root. This keeps
vehicle trunks separate from arsenal catalogs on hybrid vehicles. Loose-ground
snapshots retain the UI's item enumeration. Outgoing transfers preserve the
existing destination choice: if an ordinary single-item move targets a hybrid
vehicle's trunk, batch moves do likewise rather than automatically preferring
an arsenal refund.

ACE Inventory does **not** implement equipping, weapon attachments, controller
bindings, batch dragging, or an in-game batch-size preferences UI.

## Rebinding quantity modifiers

Open **Settings → Controls → ACE Inventory**. The **Small batch**, **Large batch**
and **All items** entries change the held key or key combination for each quantity.
These are continuous modifier bindings, not independent transfer shortcuts.
Keep the chosen key(s) held while using the existing vanilla Move binding.
Changing a quantity binding does not change Move or the configured batch size.
The native Controls menu provides saving, unbinding and resetting to defaults.
Hints use the action bindings rather than hard-coded Ctrl/Shift images.
If overlapping quantity bindings are active, large takes precedence over All,
then small.

Avoid other inventory operations while a batch is pending. Do not use this
experimental addon on a public server.

## Configuring batch sizes

Edit `SMALL_BATCH_SIZE`, `LARGE_BATCH_SIZE` and `ALL_ARSENAL_LIMIT` in
[`ACE_Inventory_Settings.c`](../../../../../addons/inventory/scripts/Game/ACE_Inventory/ACE_Inventory_Settings.c).
These are shared script constants, not in-game preferences:

```c
static const int SMALL_BATCH_SIZE = 5;
static const int LARGE_BATCH_SIZE = 10;
static const int ALL_ARSENAL_LIMIT = 100;
```

Use positive integers. Ctrl selects the small value; Ctrl + Shift selects the
large value. Both sizes apply to normal transfers, ground pickup/drop and arsenal
acquisition/returns. Availability/capacity still
limits actual completion. The configuration is checked before enabling batch shortcuts. Invalid sizes
or a nonpositive All ceiling disable batching with an explicit error, not a silent
replacement quantity. Server RPC validation accepts the configured sizes
and All, and rejects fixed-size refund snapshots exceeding the selected size.
For returns, the server enumerates the supplied source root and validates every
distinct ID against one native-style prefab/weight/ammunition group. All cannot
exceed that group's actual size or include entities from another source group.
The server independently resolves All acquisition to its configured ceiling;
the client cannot supply a larger numeric ceiling. `ALL_ITEMS` is an internal
request marker, not a batch-size setting; leave it unchanged.
Debug instrumentation and its toggle have been removed. Successful transfers,
per-item progress, normal capacity stops and menu closure do not produce logs.
Only actual errors, rejected requests and unresolved-operation timeouts are logged.

Recompile/reload the addon after changing these values. Multiplayer participants
must use the same addon version and settings. Input actions retain their existing
internal names; those names do not determine batch sizes.

## Diagnostics and completion

Look for `[ACE Inventory]` warnings/errors when an operation fails or remains
unresolved. Routine transfer/progress summaries and debug traces are absent;
verify successful quantities through the resulting inventory contents.
Unavailable modifier bindings are reported explicitly and disable batch shortcuts,
not ordinary native dragging or quick moves.

Physical moves/pickups use native operation callbacks and additionally check the
item's destination storage. Drops require a successful callback and the existing
entity no longer having a storage parent. Stack membership uses vanilla UI grouping rather than
prefab-only matching.

Arsenal requests run one at a time on the owning player-controller component.
The native one-item request performs access, catalog, supplies and allocation
validation. A narrowly scoped hook captures the spawn callback constructed
inside that request, so unrelated arsenal spawns do not advance the batch.
ACE Inventory does not manually spawn items or change supplies balances.

Refund requests use a source-group-bounded snapshot of replication IDs and
revalidate each item's original storage and refundable contents. The native one-item refund
owns resource credit, eligibility, distance checks and refund effects.
Unlike acquisition, this native API does not expose a completion callback.
A narrowly scoped hook records acceptance for the exact item, player controller
and arsenal when native `OnItemRefunded_S` runs. Installed 1.8.0.13 source confirms
this hook follows validation/resource generation and precedes deletion.
Rejected requests stop immediately without watching unrelated entity deletions.
Accepted requests then watch removal of the specific entity on the server.
Verify supplies/allocation changes as well as item counts during testing.
An accepted but unconfirmed refund stops issuing further requests after ten
seconds, without retrying. Monitoring continues at a reduced frequency so a late
removal can finish and release the batch safely.

After a callback timeout, the batch stops issuing requests and does not retry.
The outstanding operation may still complete; its result is not reported as a
failure or success until confirmed. An unresolved arsenal callback keeps that
player's server-side batch occupied until the outstanding outcome is confirmed.
Reconnect/restart the test session only if the engine never settles that operation.

Closing inventory cancels future work, not an already submitted operation.
The UI detaches from server-owned arsenal batches without treating them as
physical moves on reopening. Physical callbacks identify both batch and item index;
late callbacks cannot advance a different operation. Deleting the player-controller
component clears queued monitoring and invalidates its batch token.
Check final inventory counts and supplies after that outstanding operation settles.

initial/final supplies, and relevant diagnostics when reporting results.
