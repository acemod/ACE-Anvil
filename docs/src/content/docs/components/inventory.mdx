---
title: ACE Inventory
---

Experimental PC-only proof of concept for **modifier + right-click or drag batch transfers**,
with configurable small and large batches (default **5 and 10**) and **All that fit**.
It is not included in ACE All in One and is not production-ready.

## Loading

1. In Arma Reforger Tools, scan the repository's `addons` directory for projects.
2. Open `ACE Inventory` (`addons/inventory/addon.gproj`).
3. Ensure the local ACE Magazine Repack project is registered; ACE Inventory depends
   on it so its modified transfer path takes precedence over magazine repacking.
4. Compile Game scripts in Script Editor. Resolve compilation errors before testing.
5. Open a test world with inventory containers and an enabled arsenal.
   The development guide recommends the vanilla `MpTest` world.

The project intentionally has no resource database checked in. Allow Workbench
to generate its resource database when registering/opening the project.

## Controls and scope

**Quick transfer:** hold either Ctrl key and right-click the source stack or arsenal
catalog item for the small batch (default five). Hold **Ctrl + Shift** and
right-click for the large batch (default ten); either left/right modifier key works.
Hold **Shift without Ctrl** and right-click for **All**. Ctrl + Shift takes
precedence and selects the large batch, not All.
The quantity is captured when the batch starts, so releasing modifiers does
not change a pending batch. Incoming quick transfers use compatible player deposit storages,
regardless of which player container is displayed. Automatic
destination selection is repeated per item, so filling one pocket does not stop
a batch when another player storage can accept the remainder. Player items go
to the currently open external container. If the opposite panel is showing the
ground rather than a container, modified right-clicking a player stack drops up
to the selected quantity. Modified right-clicking a loose ground stack picks up
to that quantity. With an arsenal
open, modified right-clicking a player stack returns/refunds up to that many eligible
items rather than dropping them on the ground.

The click shortcut uses Ctrl/Shift + mouse input combinations, not the drag state.
The modifier and quick-transfer actions are attached to vanilla's active `InventoryMenuContext`;
Ctrl and Shift states are latched using the modifier actions' down/up listeners.
The earlier low-priority custom context was active but its Ctrl input was masked
by the inventory UI's higher-priority contexts.

**Drag transfer:** a retained experimental path for an explicit destination.
Hold either Ctrl key **before starting a drag**, then drop onto a different
ordinary inventory container, or onto an item tile inside that container.
Hold Shift as well before starting the drag to capture the large batch.
Hold only Shift before starting the drag to capture All.
Keep the target container open so the destination is unambiguous.

After updating the addon, stop Play mode and reload the Workbench project
(or restart Workbench), then re-enter Play mode. Recompiling Game scripts alone
does not reload changed input bindings.

- Normal inventory: move up to the selected quantity from the selected visible stack.
- Arsenal: request up to the selected quantity of the catalog item through the
  native arsenal acquisition path, or return up to that many physical items through
  the native refund path. Items containing non-refundable contents are rejected.
- Ground: insert existing loose entities into inventory, or remove stored
  entities to the ground, through the normal native pickup/drop APIs.
- Capacity, compatibility and native arsenal rules may reduce the result.
- Releasing Ctrl during the drag does not change the captured quantity.
- Unmodified dragging keeps the existing inventory/magazine-repack behavior.

For All, physical transfers and arsenal returns snapshot the entire selected
visible stack, not every matching item across inventory. They stop at source
exhaustion, changed membership, cancellation or native rejection. Items added
to the stack after the snapshot are not included. Arsenal acquisition has no
finite source stack: it requests until native rules reject the next item or the
configured All ceiling is reached (default **100 confirmed acquisitions**).
The ceiling does not truncate physical stacks or arsenal returns.

ACE Inventory does **not** implement equipping, weapon attachments, controller
bindings, or a polished/rebindable quantity UI. Unsupported Ctrl-drag targets
are rejected with the inventory error sound and a diagnostic.

Avoid other inventory operations while a batch is pending. Do not use this
experimental addon on a public server.

## Configuring batch sizes

Edit `SMALL_BATCH_SIZE`, `LARGE_BATCH_SIZE` and `ALL_ARSENAL_LIMIT` in
[`ACE_Inventory_Settings.c`](../../../../../addons/inventory/scripts/Game/ACE_Inventory/ACE_Inventory_Settings.c).
These are shared script constants, not in-game preferences:

```c
static const int SMALL_BATCH_SIZE = 5;
static const int LARGE_BATCH_SIZE = 10;
static const int ALL_ARSENAL_LIMIT = 100;
```

Use positive integers. Ctrl selects the small value; Ctrl + Shift selects the
large value. Both sizes apply to normal transfers, ground pickup/drop and arsenal
acquisition/returns, including the retained drag path. Availability/capacity still
limits actual completion. Server RPC validation accepts only the configured sizes
and All, and rejects fixed-size refund snapshots exceeding the selected size.
The server independently resolves All acquisition to its configured ceiling;
the client cannot supply a larger numeric ceiling. `ALL_ITEMS` is an internal
request marker, not a batch-size setting; leave it unchanged.

Recompile/reload the addon after changing these values. Multiplayer participants
must use the same addon version and settings. Input actions retain their existing
internal names; those names do not determine batch sizes.

Arma Reforger Workbench **1.8.0.13**. Workbench was launched with the addon project,
the repository's `addons` search path, the installed game's working directory,
and a separate test profile. Initial argument-name compiler errors were corrected.

with Game CRC `d8c34123`. Previous interactive logs confirmed several 5/5 ground
drops and capacity-limited arsenal acquisitions. User testing confirmed item
addition/removal across the tested inventory, ground and arsenal paths using
the revised controls. This confirms item movement, not supplies accounting:
arsenal supplies/allocation charges and credits have not been verified.
Exact batch quantities and the retained drag path still need recorded verification.
The configurable 5/10 implementation compiled successfully in Workbench
**1.8.0.13**, Game CRC `272bbff2`, and the user reported it working.
The All implementation compiled successfully in the same Workbench version,
Game CRC `0aee1f0d`. User testing subsequently reported **Shift + right-click
does not work in any transfer direction**. All is not runtime-validated and
its modifier/input handling is the next investigation; 5/10 were reported working.
After renaming the addon to ACE Inventory, compilation passed with Game CRC
`f918bc59`. This is a development checkpoint, not a production release.
The test matrix below still needs complete execution, including multiplayer.

## Diagnostics and completion

Look for `[ACE Inventory]` in the Workbench/game logs. A completed batch
reports its actual confirmed count, for example `3/5`, not merely requests sent.

`Drag start: quantity=5, context=1` (or `quantity=10`) confirms modifier detection
with the default settings. `quantity=-1` at drag start denotes All; batch
progress uses the snapshotted stack size or arsenal acquisition ceiling.
`Modifier+right-click detected` confirms the independent quick-transfer shortcut fired.
A `Single-item path` diagnostic shows whether modifier detection or the drag
state caused vanilla fallback. An unavailable quantity context is reported
explicitly and blocks dragging rather than silently moving one item.

Physical moves/pickups use native operation callbacks and additionally check the
item's destination storage. Drops require a successful callback and the existing
entity no longer having a storage parent. Stack membership uses vanilla UI grouping rather than
prefab-only matching.

Arsenal requests run one at a time on the owning player-controller component.
The native one-item request performs access, catalog, supplies and allocation
validation. A narrowly scoped hook captures the spawn callback constructed
inside that request, so unrelated arsenal spawns do not advance the batch.
ACE Inventory does not manually spawn items or change supplies balances.

Refund requests use a bounded snapshot of replication IDs and revalidate each
item's original storage and refundable contents. The native one-item refund
owns resource credit, eligibility, distance checks and refund effects.
Unlike acquisition, this native API does not expose a completion callback;
ACE Inventory watches removal of the specific refunded entity on the server.
Verify supplies/allocation changes as well as item counts during testing.
An unconfirmed refund stops after ten seconds without retrying and keeps the
server-side batch occupied; reconnect/restart before continuing that test.

After a callback timeout, the batch stops issuing requests and does not retry.
The outstanding operation may still complete; its result is not reported as a
failure or success until confirmed. An unresolved arsenal callback keeps that
player's server-side batch occupied. Reconnect/restart the test session if
the engine never supplies a callback.

Closing inventory cancels future work, not an already submitted operation.
Check final inventory counts and supplies after that outstanding operation settles.

## Development test matrix

Run these in single-player first, then hosted and dedicated multiplayer.

| Test | Expected result |
| --- | --- |
| Source stack of 1, 3, 5, or 7; enough room | Move 1, 3, 5, or 5 respectively |
| Ctrl + Shift + right-click, source stack of 1, 7, 10, or 12; enough room | Move 1, 7, 10, or 10 respectively |
| Large batch, destination room for only three | Move three and stop; preserve the remainder |
| Ctrl + Shift + right-click, each inventory/ground/arsenal direction | Transfer at most ten, with no eleventh request |
| Release Shift or Ctrl during a ten-item batch | Keep the captured ten-item limit |
| Change configured sizes to 3 and 7, then reload | Small/large batches cap at 3/7 across all paths; logs use those limits |
| Shift + right-click, selected physical stack larger than ten | Transfer the whole selected stack if room permits; no ten-item truncation |
| All, destination fits only part of the stack | Transfer only what fits and leave the remainder at source |
| All, selected stack versus other matching stacks | Transfer only the selected snapshot; leave other stacks untouched |
| Shift + right-click, arsenal return stack larger than 100 | Return the selected stack; acquisition ceiling does not apply |
| All acquisition, free arsenal with room for more than 100 | Stop at exactly 100 confirmed acquisitions with the default ceiling |
| Set All arsenal ceiling to 12, then reload | Acquire at most 12; physical All remains unrestricted by that ceiling |
| Ctrl + Shift + right-click with All available | Still use the configured large batch (default ten) |

| Ctrl-click source stack with opposite inventory available | Quick-transfer up to five without dragging |
| Ctrl-click arsenal item | Acquire up to five into the player container |
| Ctrl-click player stack with ground panel visible | Drop up to five existing entities |
| Ctrl-click loose ground stack | Pick up up to five, limited by available player capacity |
| Source ground item picked up by another player mid-batch | Stop when source membership changes; no duplicate |

| Cancel/close inventory during refund | Submitted native operation may settle; no further returns |
| Another player changes a refund source | Stop on changed membership; verify no duplicate credit |
| Release Ctrl during drag | Still request up to five |
| Close inventory during transfer | No further work after cancellation; pending operation may settle |
| Repeated drag while busy | Reject overlapping batch |
| Artificial latency or delayed callback | At most one item operation outstanding; accurate confirmed counts |

For physical transfers, verify exact source/destination entities and conserved
total item count. For arsenal acquisition, verify both acquired entities and the
native supplies/allocation charge. A successful compile or log message alone
does not establish multiplayer correctness.

Record the game version, environment, input gesture, initial/final counts,
initial/final supplies, and relevant diagnostics when reporting results.
